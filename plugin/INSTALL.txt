Reva AI Runtime Authorization (reva-ai-runtime-authorization) — installation
============================================================================

Authorizes agent, MCP, A2A and LLM traffic passing through Kong AI Gateway by
evaluating every call against Reva Trust Guardian.

Requires Kong AI Gateway 2.2 or later.

It is an AI Custom Policy: a schema (schema.lua) and a handler (handler.lua).
Kong AI Gateway runs a custom policy in one of two ways; this one works with
either. Pick one of sections 1 and 2, then continue at section 3.


1. STREAMING POLICY (no change to the data plane image)
-------------------------------------------------------

Konnect stores the schema and the handler and sends the handler to every data
plane.

Start every data plane with:

    KONG_CUSTOM_PLUGIN_STREAMING_ENABLED=on
    KONG_UNTRUSTED_LUA=lax

The policy makes an outbound HTTPS call to Reva Trust Guardian, which the
default strict Lua sandbox blocks.

Create an AI Custom Policy in Konnect (UI, AI Gateway API or kongctl). The API
call is POST /v1/ai-gateways/{aiGatewayId}/custom-policies with:

    name      reva-ai-runtime-authorization
    type      streaming
    schema    the contents of schema.lua
    handler   the contents of handler.lua

The name must match the name declared in the schema. Neither name nor type can
be changed afterwards.


2. INSTALLED POLICY (code on each data plane)
---------------------------------------------

Konnect receives only the schema. The code must be on every data plane node.

Option A — Docker / Kubernetes: build the data plane image with the policy in
it.

    FROM kong/kong-ai-gateway:2.3.0-distroless
    COPY kong/plugins/reva-ai-runtime-authorization /usr/local/share/lua/5.1/kong/plugins/reva-ai-runtime-authorization
    ENV KONG_PLUGINS=bundled,reva-ai-runtime-authorization

Option B — LuaRocks, from the packed rock, then enable it in kong.conf:

    luarocks install kong-plugin-reva-ai-runtime-authorization-2.0.0-1.all.rock

    plugins = bundled,reva-ai-runtime-authorization

or as an environment variable:

    KONG_PLUGINS=bundled,reva-ai-runtime-authorization

Option C — from source:

    luarocks make

Restart the data plane. A code change requires a restart — Kong loads Lua at
worker startup, so a configuration sync alone is not enough.

Then create an AI Custom Policy in Konnect with name
reva-ai-runtime-authorization, type installed and schema set to the contents of
schema.lua. Do not send a handler.


3. ATTACH AND CONFIGURE
-----------------------

Create an AI Policy whose type is reva-ai-runtime-authorization. It has no scope
restriction: attach it globally, or to an AI Model, AI Consumer or AI Consumer
Group.

auth_token is required; everything else has a working default.

    reva_host         optional; defaults to api.reva.ai. Override with your
                      tenant host or base URL, e.g. api.example.reva.ai
    auth_token        bearer token Kong presents to Reva Trust Guardian.
                      Use a vault reference in production.

The policy evaluates every matching call against Reva Trust Guardian on
reva_host. The user comes from the JWT. An allow returns a transaction token,
which the policy adds to the upstream request.

Example AI Policy configuration:

    reva_host: api.example.reva.ai
    auth_token: "{vault://env/reva-ai-runtime-authorization-token}"

auth_token is referenceable: in production give it a vault reference, such as
the one above, rather than a literal.


4. REQUEST BUFFERING
--------------------

The policy reads the request body, so routes it covers need:

    request_buffering: true

MCP endpoints stream over SSE and additionally need:

    response_buffering: false


5. WHAT YOUR APPLICATION MUST FORWARD
-------------------------------------

The policy joins the hops of one turn only if every service in the chain passes
on what it received. Each agent must send these headers, spelled as shown, on
every call it makes through the gateway: to a model, an MCP server or another
agent.

    Authorization: Bearer <JWT>   on every call. The end user's token, unchanged.
                                  A call without it is refused with 401.
    traceparent                   on every call. Start one per user message, then
                                  forward it unchanged. Without it Reva cannot
                                  link a call to its turn.
    X-Transaction-Token           on every call after the first. Issued by Reva
                                  Trust Guardian and added by the policy to the
                                  upstream request. Forward it exactly as
                                  received. Its presence marks a later hop.
    the thread id                 on the first call of a turn only, at the place
                                  session_key names (default: the header
                                  X-Reva-Session-Id).

A call with no X-Transaction-Token is treated as the first call of a turn: the
user comes from the JWT, and the thread id is read. A call that carries one is a
later hop: Reva takes the agent and the user from the token, and no thread id is
needed.

The transaction token is short-lived. A call made after it has expired is
refused with "authorization service unavailable", and the data plane log shows
"X-Transaction-Token validation failed".


6. VERIFY
---------

Send a call with no Authorization bearer. The policy should reject it itself,
which proves it is loaded and running:

    curl -i -X POST http://localhost:8000/<your-model-route> \
      -H 'Content-Type: application/json' \
      -d '{"model":"gpt-4o","messages":[{"role":"user","content":"hi"}]}'

    HTTP/1.1 401
    {"message":"Blocked by Reva","reason":"missing Authorization bearer token"}

Then repeat with a JWT (the claim named by jwt_user_claim, default sub):

    -H 'Authorization: Bearer <jwt>'

Decisions are logged at info level, one line per call:

    [reva-ai-runtime-authorization] invokeModel gpt-4o allowed=true status=200 latency_ms=412.3

When the first call of a turn completes, the policy reports the turn to Reva
Trust Guardian, on a best-effort basis. A streamed A2A response (message/stream)
is passed through as it is produced and is not reported.

KONG_LOG_LEVEL must be info or lower; notice hides the decision trail.
